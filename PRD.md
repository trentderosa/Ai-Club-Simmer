# Simmer — Product Requirements Document (MVP)

*Learn to cook, one dish at a time.*
JMU AI Club · Fall 2026 · Team: Trent DeRosa, Ezzeldin Mallek, Nathan Biru, Ian Bullette, Matthew Munoz
Status: **Draft** · Last updated: 2026-11-02 · Target demo: ~early January 2027 (2 months)

---

## 1. Overview

Simmer is a mobile app that helps new cooks build skills step by step — "the Duolingo of cooking." Instead of a pile of recipes, it gives the user a short, ordered learning path where each recipe teaches a technique, explains why it matters, and links a video showing it.

**Problem it solves:** Many people, especially college students living alone for the first time, want to cook but don't know where to start. Recipes assume basic knowledge ("sauté until fragrant"), recipe apps don't teach skills in a logical order, and nothing keeps beginners motivated, so they fall back on the same few meals or takeout.

**Core loop (MVP):** Plan → Cook → Check in → Level up (XP and badges) → next recipe, with the AI tailoring tips after each check-in.

## 2. Users

- **Primary:** College students and young adults who are new to cooking, have limited equipment and budget, and cook for themselves.
- **Demo audience:** JMU AI Club members and showcase attendees, who'll see the app run end to end.

## 3. Goals and success criteria

**Goal:** Help a beginner go from needing detailed instructions for every step to cooking a dish with the instructions hidden.

**MVP success criteria (for the showcase):**
1. A brand-new user can go through the full loop on a phone, live: sign up → onboarding → see their plan → cook a recipe with AI-generated steps and a technique video → complete a check-in → earn XP and a badge → see the next recipe's tips reflect their feedback.
2. The user can reach and complete the mastery challenge on the final recipe, earn the mastery badge, and see the recipe in their recipe book.
3. The demo runs without crashes on the demo-day setup (one laptop running the AI server, phones on the same network or tunnel).

(Targets for user testing with people outside the team are an open question.)

## 4. Features

### F1. Sign-up and onboarding
New users create an account and answer a short onboarding form: cooking goals, experience level, kitchen equipment, budget, and weekly schedule (how many days/how much time they can cook).

**Acceptance criteria**
- [ ] A user can sign up, log in, and log out using Supabase Auth (email + password).
- [ ] After first sign-up, the user is taken through onboarding before seeing the rest of the app.
- [ ] Onboarding collects: goals, experience level (e.g., never cooked / a little / comfortable), equipment (multi-select checklist), budget (low / medium / high), and schedule (days per week and minutes per session).
- [ ] Answers are saved to the user's profile in Supabase and can be edited later from a settings or profile screen.
- [ ] A returning user who has finished onboarding goes straight to their plan.

### F2. Personalized plan (one fixed path)
Every user gets the same path, **"Weeknight basics"**: 10 dish slots in a fixed order (e.g., knife basics, eggs, pasta, stir-fry, …, roast chicken as the final mastery challenge). Personalization comes from how the recipes are written for the user (F3) and from a suggested cooking schedule.

**Acceptance criteria**
- [ ] The 10 path slots (dish name, technique focus, XP value, order) are defined in the database, not generated by the AI.
- [ ] The plan screen shows all 10 slots as **done / current / locked**, matching Figure 2 of the proposal.
- [ ] Only the current slot can be started. Finishing a slot (cook + check-in) unlocks the next one.
- [ ] The plan shows a suggested number of cooking sessions per week based on the user's onboarding schedule.
- [ ] The final slot is marked as the mastery challenge.

### F3. AI-generated recipes
When a user opens a path slot for the first time, the app asks the local Ollama model to generate a recipe for that dish, tailored to the user's equipment, budget, and experience. The recipe is saved, and the same saved recipe is used every time after that.

**Acceptance criteria**
- [ ] The AI server calls Ollama with a JSON schema (structured output). The recipe has: title, ingredients (with amounts), time estimate, ordered steps, and for each step: instruction text, an optional "why it matters" note, a `is_safety_step` flag, and an optional technique name for video lookup.
- [ ] The response is validated against the schema. Invalid output is retried up to 2 times, then the app shows a clear error with a retry button.
- [ ] The generated recipe is saved to Supabase for that user and slot, and isn't regenerated on later visits.
- [ ] The prompt includes the user's equipment, budget, and experience, and tells the model not to use equipment the user doesn't have.
- [ ] Steps involving heat, knives, boiling water, raw meat, or hot oil are flagged as safety steps.
- [ ] Generation shows a loading state, and the user can't start cooking until the recipe has loaded.

### F4. Technique videos
Each recipe step with a technique name gets an instructional video found through the YouTube Data API.

**Acceptance criteria**
- [ ] For each distinct technique in a recipe, the AI server runs one YouTube search (e.g., "how to dice an onion beginner") and saves the top result's video ID with the recipe.
- [ ] Video results are cached per technique so the same search isn't repeated for other users (this saves API quota).
- [ ] In cook mode, a step with a video shows a thumbnail or button that plays the video inside the app.
- [ ] If the search fails or returns nothing, the step still shows without a video and the recipe keeps working.

### F5. Cook mode
A step-by-step screen the user follows while cooking.

**Acceptance criteria**
- [ ] Shows the ingredient list first, then one step at a time with Next/Back buttons.
- [ ] Each step shows its instruction, its "why it matters" note (if any), and its video (if any).
- [ ] Safety steps are visually marked (e.g., red border and a "Safety" label).
- [ ] The final step leads to a "Done cooking" action, which opens the check-in (F6).

### F6. Feedback check-in and tip adjustment
After cooking, the user does a quick check-in. The AI uses it to rewrite tips for the next recipe. The path order never changes.

**Acceptance criteria**
- [ ] The check-in asks for a difficulty rating (easy / OK / hard), "What went well?" (optional text), and "What was hard?" (optional text).
- [ ] The check-in is saved to Supabase with the user, recipe, and timestamp.
- [ ] Completing the check-in marks the slot as done, unlocks the next one, and awards XP (F7).
- [ ] When the next recipe is generated (F3), the prompt includes the user's recent check-ins, and the recipe includes a short "Coach's note" at the top that references them (e.g., "Last time heat control was tricky, so watch for…").
- [ ] If the user rated the session "hard," the app suggests repeating that recipe before moving on. The user can accept or skip.
- [ ] Check-ins don't reorder, swap, or remove path slots.

### F7. XP with caps
Users earn XP for finishing recipes. Harder recipes are worth more, and repeating easy recipes is capped so users can't farm XP.

**Acceptance criteria**
- [ ] Each path slot has a fixed XP value that goes up along the path (proposal example: 40, 50, 60, 80 … 150 for the mastery challenge).
- [ ] XP is awarded once per completed check-in for that slot.
- [ ] Repeating an already-completed recipe earns reduced XP *(proposed: 50% of its value)*, up to a weekly repeat cap *(proposed: 100 XP per week)*. Repeats over the cap earn 0 XP, and the app says so.
- [ ] The user's total XP is shown on the plan screen, and XP gains show briefly after a check-in.
- [ ] XP is calculated and saved on the server side (database function or AI server), not trusted from the client.
- [ ] After a check-in is saved, the AI server awards XP by calling `award_slot_xp` with the service role (the client never calls it). If the award fails, the check-in stays saved and the error is logged.
- [ ] Client roles (`PUBLIC`, `anon`, `authenticated`) have `EXECUTE` revoked on `public.rls_auto_enable()`, the event-trigger helper owned by Nathan and Ezzeldin. The function body is unchanged, and the revoke is guarded so it is a no-op on databases that don't have the function. Approved by Trent on Nov 12, 2026.

### F8. Mastery challenge (final path recipe only)
The user cooks the final recipe with the steps hidden, revealing individual steps only when they need help. Safety steps always stay visible.

**Acceptance criteria**
- [ ] Only the final path slot (slot 10) is a mastery challenge.
- [ ] In challenge mode, all steps start hidden except safety steps, which are always shown (proposal Figure 3).
- [ ] Each hidden step has a Reveal button, and the screen shows "Revealed X of Y hidden steps."
- [ ] Finishing the challenge and completing the check-in counts as **passing**. No photo is required.
- [ ] Passing awards the slot's XP and the mastery badge (F9), and adds the recipe to the recipe book (F10) labeled Mastered.

### F9. Badges
**Acceptance criteria**
- [ ] **Completion badge:** earned for each of slots 1–9 after cooking it and completing the check-in.
- [ ] **Mastery badge:** earned for passing the mastery challenge (F8).
- [ ] **Path milestone badge:** earned for finishing all 10 slots of "Weeknight basics."
- [ ] A badges screen shows earned badges and locked (grayed-out) ones.
- [ ] Earning a badge shows a short celebration on screen.
- [ ] Each badge can only be earned once.

### F10. Recipe book
**Acceptance criteria**
- [ ] Every recipe the user completes (cooked + check-in done, slots 1–10) is saved to their personal recipe book.
- [ ] Each entry is labeled **Completed** or **Mastered**. Passing the mastery challenge (F8) marks that recipe as Mastered.
- [ ] The recipe book lists saved recipes, and tapping one opens the full recipe (ingredients, steps, videos) in a read-only view.
- [ ] A recipe appears only once, even if the user cooks it again.
- [ ] An empty recipe book shows a message explaining how to add recipes.

## 5. Out of scope (MVP)

Do **not** build these. They're future work.

- Step-ordering exercise ("put the steps in order")
- Cooking levels (L1–L4)
- Weekly leagues and leaderboards, both individual and team
- Per-recipe variations
- Calendar sync (Google Calendar) and grocery cart integration (Walmart or other retailers), and any grocery XP
- The two-week bigger checkpoint
- AI reordering, swapping, or rebuilding the path
- Photo upload of the finished dish, and the "cook it twice" mastery requirement
- Mastery challenges for any recipe other than the final path slot
- More than one learning path
- Hosted LLM APIs (OpenAI, Anthropic, Gemini, etc.)
- Social features (friends, sharing, comments)
- App store publishing (the demo runs through Expo Go or a dev build)

## 6. Tech stack and constraints

| Area | Choice |
|---|---|
| App | React Native with **Expo** (TypeScript), run through Expo Go or a dev build |
| Backend / DB | **Supabase**: Postgres, Auth (email + password), row-level security so users only see their own data |
| AI | **Ollama** running a local model (~7–8B, e.g., a Llama or Qwen model) on **one team laptop** |
| AI server | A small proxy on the same laptop that the app calls. It verifies the user's Supabase login token, calls Ollama with structured JSON output, calls the YouTube API, and writes results to Supabase |
| Network | Phones reach the AI server over the same Wi-Fi or through a tunnel (ngrok or Cloudflare Tunnel) |
| Videos | YouTube Data API v3 (search), with results cached in Supabase |

**Constraints**
- **Timeline:** ~2 months to a working demo. The team is part-time students.
- **The AI only works while the AI-server laptop is running Ollama and the proxy.** Recipes that are already generated and saved still load without it.
- **Secrets:** The YouTube API key and Supabase service-role key live only on the AI server, never in the app.
- **YouTube quota:** The default quota is 10,000 units/day, and each search costs 100 units (about 100 searches/day), so searches must be cached.
- **Cost:** Use free tiers (Supabase free plan, YouTube free quota, local model).

**Development workflow (Git)**
- **Nobody commits or pushes directly to `main`.**
- Each feature or change gets its own branch, named after it, for example `feature/f1-signup-onboarding`, `feature/f7-xp-caps`, or `fix/recipe-schema-retry`.
- All commits for that change go on its branch.
- When the change is ready, open a **pull request** into `main`. The PR description lists the feature (F#) and which acceptance criteria are met.
- At least one other teammate reviews and approves the PR before it's merged into `main`.
- Turn on GitHub branch protection for `main` (require a PR and 1 approval) so this is enforced.

## 7. Open questions

1. **Exact demo date.** The proposal still says `[demo date]`. We're assuming about 2 months from 2026-11-02.
2. **Back-end/database owner.** The proposal lists this as TBD (Matthew?). Someone also needs to own the AI-server laptop setup.
3. **Team hours per week.** Not yet known. This affects whether everything in F1–F10 fits.
4. **Mastery pass threshold.** Right now finishing the challenge counts as passing, no matter how many steps were revealed. Should there be a reveal limit (e.g., at most 2 reveals)?
5. **XP numbers.** The full set of 10 slot values, the repeat XP percentage, and the weekly cap still need to be confirmed (proposed: 50% and 100 XP/week).
6. **Local model quality and safety.** Small models make more mistakes in recipes and safety flags. Should the team review the generated recipes for the 10 slots before the demo, and which exact model should we use?
7. **Video accuracy.** Taking the top YouTube result may sometimes return off-target or low-quality videos. Is that acceptable, or should someone check the cached videos for the 10 slots?
8. **User testing.** Should we test with people outside the team before the showcase, and what targets should we set (e.g., 5 testers, 2 recipes each)?
9. **The 10 path dishes.** The proposal names 5 (knife basics, eggs, pasta, stir-fry, roast chicken). Which 5 go in between, and in what order?
