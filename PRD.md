# Simmer — Product Requirements Document (MVP)

*Learn to cook, one dish at a time.*
JMU AI Club · Fall 2026 · Team: Trent DeRosa, Ezzeldin Mallek, Nathan Biru, Ian Bullette, Matthew Munoz
Status: **Draft** · Last updated: 2026-11-16 · Target demo: ~early January 2027 (2 months)

---

## 1. Overview

Simmer is a mobile app that helps new cooks build skills step by step — "the Duolingo of cooking." Instead of a pile of recipes, it gives the user a short, ordered learning path where each recipe teaches a technique, explains why it matters, and links a video showing it.

**Problem it solves:** Many people, especially college students living alone for the first time, want to cook but don't know where to start. Recipes assume basic knowledge ("sauté until fragrant"), recipe apps don't teach skills in a logical order, and nothing keeps beginners motivated, so they fall back on the same few meals or takeout.

**Core loop (MVP):** Plan → Cook → Check in → Level up (XP and badges) → next recipe, with the AI tailoring tips after each check-in. Users can also type a dish outside the path ("Cook anything") and go through the same cook and check-in loop.

## 2. Users

- **Primary:** College students and young adults who are new to cooking, have limited equipment and budget, and cook for themselves.
- **Demo audience:** JMU AI Club members and showcase attendees, who'll see the app run end to end.

## 3. Goals and success criteria

**Goal:** Help a beginner go from needing detailed instructions for every step to cooking a dish with the instructions hidden.

**MVP success criteria (for the showcase):**
1. A brand-new user can go through the full loop on a phone, live: sign up → onboarding → see their plan → cook a recipe with AI-generated steps and a technique video → complete a check-in → earn XP and a badge → see the next recipe's tips reflect their feedback.
2. The user can reach and complete the mastery challenge on the final recipe, earn the mastery badge, and see the recipe in their recipe book.
3. The demo runs without crashes on the demo-day setup (one laptop running the AI server, phones on the same network or tunnel).

(Targets for user testing with people outside the team are an open question.)

## 4. Features

### F1. Sign-up and onboarding
New users create an account and answer a short onboarding form: cooking goals, experience level, kitchen equipment, budget, and weekly schedule (how many days/how much time they can cook).

**Acceptance criteria**
- [ ] A user can sign up, log in, and log out using Supabase Auth (email + password).
- [ ] After first sign-up, the user is taken through onboarding before seeing the rest of the app.
- [ ] Onboarding collects: goals, experience level (e.g., never cooked / a little / comfortable), equipment (multi-select checklist), budget (low / medium / high), and schedule (days per week and minutes per session).
- [ ] Answers are saved to the user's profile in Supabase and can be edited later from a settings or profile screen.
- [ ] A returning user who has finished onboarding goes straight to their plan.

*Client (`app/`, UI Direction A):* sign up and sign in are on one screen (email + password). The first name is saved in auth `user_metadata.first_name` for the greeting and the profile, since `profiles` has no name column. Onboarding is steps 2–4 of 4 (about you, your kitchen, your week) and upserts the user's own `profiles` row with `onboarding_completed: true`. The diet question from the mockups is left out because there's no column for it. Users with `onboarding_completed` not `true` are routed to onboarding; everyone else goes straight to Today. The profile shows those answers and can edit them with the same steps and columns. Sign-out is on the profile.

### F2. Personalized plan (one fixed path)
Every user gets the same path, **"Weeknight basics"**: 10 dish slots in a fixed order (e.g., knife basics, eggs, pasta, stir-fry, …, roast chicken as the final mastery challenge). Personalization comes from how the recipes are written for the user (F3) and from a suggested cooking schedule.

**Acceptance criteria**
- [ ] The 10 path slots (dish name, technique focus, XP value, order) are defined in the database, not generated by the AI.
- [ ] The plan screen shows all 10 slots as **done / current / locked**, matching Figure 2 of the proposal.
- [ ] Only the current slot can be started. Finishing a slot (cook + check-in) unlocks the next one.
- [ ] The plan shows a suggested number of cooking sessions per week based on the user's onboarding schedule.
- [ ] The final slot is marked as the mastery challenge.

*Server side (PR #11, migration `20261115000000_plan_badges_recipe_book.sql`):* a slot is **done** once the user has at least one check-in for it. **Current** is the first slot that isn't done, and everything after it is **locked**. The app reads this with `get_my_plan()`, and `get_my_plan_summary()` gives total XP and the suggested sessions per week (rule in open question 11). The AI server enforces path order: `POST /api/recipes/generate/:slotId` returns `403 SLOT_LOCKED` for a locked slot. Done slots stay open so they can be repeated, and saved recipes always load when the slot is known. If the path-slot lookup comes back empty, the call returns 404 even if a saved recipe exists, so hidden step text is never returned unmasked. See `docs/CLIENT_API.md`.

*Client (`app/`, UI Direction A):* Today reads `get_my_plan()` and `get_my_plan_summary()` and shows the next dish, the suggested sessions per week, total XP, all 10 slots as done / current / locked, and the final slot as the mastery challenge. Locked slots can't be opened. It re-reads both after a check-in. A "Cook anything" card on Today opens the free-form dish flow (F11); it does not change path order.

### F3. AI-generated recipes
When a user opens a path slot for the first time, the app asks the local Ollama model to generate a recipe for that dish, tailored to the user's equipment, budget, and experience. The recipe is saved, and the same saved recipe is used every time after that.

**Acceptance criteria**
- [ ] The AI server calls Ollama with a JSON schema (structured output). The recipe has: title, ingredients (with amounts), time estimate, ordered steps, and for each step: instruction text, an optional "why it matters" note, a `is_safety_step` flag, and an optional technique name for video lookup.
- [ ] The response is validated against the schema. Invalid output is retried up to 2 times, then the app shows a clear error with a retry button.
- [ ] The generated recipe is saved to Supabase for that user and slot, and isn't regenerated on later visits.
- [ ] The prompt includes the user's equipment, budget, and experience, and tells the model not to use equipment the user doesn't have.
- [ ] Steps involving heat, knives, boiling water, raw meat, or hot oil are flagged as safety steps.
- [ ] Generation shows a loading state, and the user can't start cooking until the recipe has loaded.

*Server side:* the AI server now reads the slot and the user's onboarding answers from Supabase (these were stubs that returned nothing, so live generation always failed with 404). The prompt also includes the user's last 3 check-ins, which drive the Coach's note (F6).

*Client (`app/`, UI Direction A):* the recipe screen calls `POST /api/recipes/generate/:slotId` with the user's access token, shows a loading state while the recipe is written (with a longer message after a few seconds), and maps each error to a screen: Retry for `500`, sign in again for `401`, back to the path for `403 SLOT_LOCKED`, and finish onboarding for the onboarding `404`. The Coach's note (F6) shows above the ingredients.

### F4. Technique videos
Each recipe step with a technique name gets an instructional video found through the YouTube Data API.

**Acceptance criteria**
- [ ] For each distinct technique in a recipe, the AI server runs one YouTube search (e.g., "how to dice an onion beginner") and saves the top result's video ID with the recipe.
- [ ] Video results are cached per technique so the same search isn't repeated for other users (this saves API quota).
- [ ] In cook mode, a step with a video shows a thumbnail or button that plays the video inside the app.
- [ ] If the search fails or returns nothing, the step still shows without a video and the recipe keeps working.
- [ ] A failed search (quota, network, timeout) is not saved as "no video". The recipe's videos are saved only when every technique got an answer, so a failed lookup is retried the next time the recipe is opened.
- [ ] Video lookup never holds up a recipe for long: a recipe's searches run at the same time under one time budget (default 8 seconds), and the recipe is returned with whatever videos were found by then.

*Server side:* the search query is "how to {technique} beginner cooking" (safe search, embeddable videos only). Results, including "no result", are cached per technique in `technique_videos`; a cached "no result" is retried after 7 days. A recipe makes at most 6 new searches, run concurrently under `VIDEO_LOOKUP_BUDGET_MS` (default 8000 ms). Videos are saved in `user_recipes.video_ids` and returned as `videos[techniqueName]`, but only when the lookup is complete: if any search failed, timed out, ran past the budget or was skipped by the cap, `video_ids` stays empty and the lookup runs again on the next visit (searches that worked are already in the shared cache). A genuine "no result" counts as complete. Requires `YOUTUBE_API_KEY` on the AI server; without it, recipes have no videos.

*Client (`app/`, UI Direction A):* a step's video is `videos[step.techniqueName]`; a missing entry just means no video, and `null` is treated as `{}`. Thumbnails come from `i.ytimg.com`. Tapping opens YouTube with React Native `Linking` only when the URL is on the allowlist (`https://www.youtube.com`, `https://youtube.com`, `https://m.youtube.com`, `https://youtu.be`); the server validates the same list. Mock placeholder videos are disabled and do nothing (no crash, no error toast).

### F5. Cook mode
A step-by-step screen the user follows while cooking.

**Acceptance criteria**
- [ ] Shows the ingredient list first, then one step at a time with Next/Back buttons.
- [ ] Each step shows its instruction, its "why it matters" note (if any), and its video (if any).
- [ ] Safety steps are visually marked (e.g., red border and a "Safety" label).
- [ ] The final step leads to a "Done cooking" action, which opens the check-in (F6).

*Client (`app/`, UI Direction A):* cook mode shows one step at a time with Next/Back, the step's "why it matters" note, a red-bordered Safety box on safety steps, the step's video, highlighted ingredient words, and an inline countdown timer when the step text names a time (e.g. "about 3 minutes"). The last step's button is Done cooking, which opens the check-in.

### F6. Feedback check-in and tip adjustment
After cooking, the user does a quick check-in. The AI uses it to rewrite tips for the next recipe. The path order never changes.

**Acceptance criteria**
- [ ] The check-in asks for a difficulty rating (easy / OK / hard), "What went well?" (optional text), and "What was hard?" (optional text).
- [ ] The check-in is saved to Supabase with the user, recipe, and timestamp.
- [ ] Completing the check-in marks the slot as done, unlocks the next one, and awards XP (F7).
- [ ] When the next recipe is generated (F3), the prompt includes the user's recent check-ins, and the recipe includes a short "Coach's note" at the top that references them (e.g., "Last time heat control was tricky, so watch for…").
- [ ] If the user rated the session "hard," the app suggests repeating that recipe before moving on. The user can accept or skip.
- [ ] Check-ins don't reorder, swap, or remove path slots.

*Server side:* the check-in response includes `suggest_repeat: true` when the rating is "hard". The app offers "cook again" (the slot stays open) or "skip". Nothing on the path changes either way.

*Client (`app/`, UI Direction A):* the check-in screen sends the rating and optional notes (max 500 characters) to `POST /api/check-ins`, after reading `user_recipes.id` for the slot. Each attempt gets a client-generated `idempotency_key` (from `expo-crypto`, so it works on Hermes as well as web) that is reused on Retry, so a timed-out check-in cannot be saved or awarded twice. After a network or timeout error the screen re-reads `get_my_plan()` and goes to session complete without posting again if that slot's `times_completed` already went up. If saving takes more than about 15 seconds, the screen explains that the coach is writing a note. When `suggest_repeat` is true, the session-complete screen asks "That one was tough. Cook it again before moving on?" with Cook again and Skip.

### F7. XP with caps
Users earn XP for finishing recipes. Harder recipes are worth more, and repeating easy recipes is capped so users can't farm XP.

**Acceptance criteria**
- [ ] Each path slot's XP is computed from its inputs in `path_slots` (steps, ingredients, and cook_minutes) with the approved formula:

  XP = max(1, round((steps×0.45 + ingredients×0.35 + cook_minutes×0.2)×10))

  The weights (0.45, 0.35, 0.2) and the ×10 multiplier live in `xp_config`. PostgreSQL `NUMERIC` `round()` rounds halves away from zero. The formula applies only when steps, ingredients, and cook_minutes are all set; slots missing an input keep their stored `xp_value`. Current slot inputs and XP, in path order (steps / ingredients / cook_minutes):

  1. Knife Basics Salad — 6/10/20 → 102
  2. Scrambled Eggs — 7/3/10 → 62
  3. Pasta with Sauce — 4/6/18 → 75
  4. Stir-Fry Vegetables — 6/13/35 → 143
  5. Grilled Cheese — 4/3/18 → 65
  6. Rice Bowl — 6/8/25 → 105
  7. Sheet Pan Vegetables — 5/11/38 → 137
  8. Seared Chicken Breast — 5/5/20 → 80
  9. Simple Soup — 5/13/40 → 148
  10. Roast Chicken — 3/2/80 → 181
- [ ] XP is awarded once per completed check-in for that slot.
- [ ] Repeating an already-completed recipe earns 50% of its value, up to a weekly repeat cap of 100 XP per week. Confirmed in Ian's final XP spec (gamification owner), relayed Nov 10, 2026; implemented in PR #5 (merged ca3deff, migration 20261110210000_xp_formula_weights.sql). Repeats over the cap earn 0 XP, and the app says so.
- [ ] The user's total XP is shown on the plan screen, and XP gains show briefly after a check-in.
- [ ] XP is calculated and saved on the server side, not trusted from the client. `award_slot_xp` is EXECUTE-granted to `service_role` only (PR #6, merged as `7fb5b24`). The client never calls it, and only the ai-server awards XP.
- [ ] After a check-in is saved, the AI server awards XP by calling `award_slot_xp` with the service role (the client never calls it). If the award fails, the check-in stays saved and the error is logged.
- [ ] The AI server's `award_slot_xp` call times out after `XP_AWARD_TIMEOUT_MS` (default 5000 ms). A timeout counts as a failed award: the check-in stays saved, the response says `xp: { status: "failed" }`, and `xp_award_failed` is logged with `reason: "timeout"`.
- [ ] Failed or missing awards are retried by the reconcile job (`npm run reconcile:xp` in `ai-server/`). It finds path check-ins with no `xp_events` row and Cook anything check-ins with no `generated_recipe_xp_events` row, created in the lookback window (default the last 168 hours, skipping ones younger than 120 seconds, at most 100 per run across both), oldest first. It re-runs `award_slot_xp` or `award_generated_recipe_xp` with the service role. Running it again, or twice at once, never double-awards: `UNIQUE(check_in_id)` on each XP table rejects a second award, and the job counts that as already awarded. The job is run by hand for now and isn't scheduled. No new migration: both scans are anti-joins on the existing foreign keys.
- [ ] Client roles (`PUBLIC`, `anon`, `authenticated`) have `EXECUTE` revoked on `public.rls_auto_enable()`, the event-trigger helper owned by Nathan and Ezzeldin. The function body is unchanged, and the revoke is guarded so it is a no-op on databases that don't have the function. Approved by Trent on Nov 12, 2026.

*Client (`app/`, UI Direction A):* Today shows total XP. Session complete shows `+xp_awarded` when `xp.status` is `awarded`, explains half-XP repeats and the weekly cap, and shows the totals before and after. When `xp.status` is `failed` it says the check-in is saved and the XP is on its way, with no number; `skipped` says XP isn't set up on that server.

### F11. Cook anything (free-form dish)
The user can type a dish name from Today and get an AI-generated recipe fitted to their kitchen, then cook it and check in through the same screens as a path slot. The 10-slot path is unchanged.

**Acceptance criteria**
- [ ] Today has a "Cook anything" entry. The user types a dish (empty, junk, and injection-like input are rejected; the trimmed name is capped at 80 characters). The screen has loading, empty, and error states.
- [ ] The AI server generates the recipe through the existing Ollama recipe path and looks up YouTube videos the same way as a path slot. The first validated recipe for that user and normalized dish name is reused (`cached: true`); a later request or "reroll" cannot change the stored steps, ingredients, minutes, or XP.
- [ ] Dish names are normalized as lowercase, trimmed, collapsed whitespace, punctuation stripped. The recipe is owner-only (RLS). Uncached generations are rate-limited per user (default 5 per hour).
- [ ] After cooking, the user checks in through `POST /api/check-ins` with `generated_recipe_id` (not a path `slot_id`). Check-ins are idempotent, the same way as path check-ins.
- [ ] Free-form XP uses the same slot formula, `max(1, round((steps×0.45 + ingredients×0.35 + cook minutes×0.2) × scale))`, from `xp_config`. Steps and ingredients are counted from the validated saved recipe arrays, not a model-reported number. Counts used for XP are clamped to explicit config bounds (steps 1–10, ingredients 1–12, minutes 1–45); the saved recipe body is not truncated. Example: the mock recipe (5 steps, 6 ingredients, 20 minutes) has xp_value 84. An inflated 50/80/999 response stores the full recipe and an xp_value of 177, below roast chicken (181). The daily cap (`freeform_daily_cap`, default 200) still applies when today's slot XP plus free-form XP would exceed it, so a lone max award of 177 is not itself capped.
- [ ] Repeats of the same normalized dish earn 50% XP and share the existing 100 XP/week repeat cap with path-slot repeats. Free-form awards also apply a daily cap (`freeform_daily_cap`, default 200) that counts today's slot XP and free-form XP together. Awards run only on the server via the service role (`award_generated_recipe_xp`). The 10-slot path first-completion awards are not blocked by the daily cap.
- [ ] If `award_generated_recipe_xp` fails after the check-in is saved, the check-in stays saved (`xp.status` `failed`) and the same reconcile job retries it. A second award is rejected by `UNIQUE(check_in_id)` on `generated_recipe_xp_events`.
- [ ] Video cards open allowlisted YouTube URLs only. Mock placeholders do nothing gracefully.

*Server side (migration `20261115180000_cook_anything.sql`):* `user_generated_recipes` is unique on `(user_id, normalized_dish_name)`. A BEFORE INSERT trigger clamps counts and freezes `xp_value`; a BEFORE UPDATE trigger refuses to raise those inputs. `get_user_total_xp` and `get_my_plan_summary` include free-form XP. Clamp bounds were set by Trent (1–10 / 1–12 / 1–45 → xp_value 177, below the hardest path slot, roast chicken at 181). The daily cap remains 200.

*Client (`app/`, UI Direction A):* Today opens `/cook-anything`. A successful generate goes to `/generated/[recipeId]`, then `/generated-cook`, `/generated-check-in`, and `/generated-complete`. Mock mode returns a canned 5/6/20 recipe worth 84 XP and reuses it on the same normalized name.

### F8. Mastery challenge (final path recipe only)
The user cooks the final recipe with the steps hidden, revealing individual steps only when they need help. Safety steps always stay visible.

**Acceptance criteria**
- [ ] Only the final path slot (slot 10) is a mastery challenge.
- [ ] In challenge mode, all steps start hidden except safety steps, which are always shown (proposal Figure 3).
- [ ] Each hidden step has a Reveal button, and the screen shows "Revealed X of Y hidden steps."
- [ ] Finishing the challenge and completing the check-in completes slot 10. No photo is required. This awards the slot's XP and adds the recipe to the recipe book (F10) labeled Mastered. Path completion and the graduate badge are unchanged, no matter how many steps were revealed.
- [ ] The mastery badge (F9) is awarded only when the final-slot check-in has `revealed_steps = 0`. A check-in without a mastery session earns no badge. XP is not affected.
- [ ] Reveals are tracked by the server. The app never receives a hidden step's text until the user reveals it, and the reveal count on the check-in comes from the server, not the app.

*Server side:* hidden steps are served only on reveal (migration `20261116000000_mastery_sessions.sql`, follow-up to Q4).
- The recipe call for slot 10 returns hidden steps masked: placeholder text, no "why it matters", `isHidden: true`. Technique names stay, so their videos still show. If the path-slot lookup comes back empty, the call returns 404 even when a saved recipe exists, so hidden step text is never returned unmasked.
- Cook mode calls `POST /api/mastery/sessions`, which starts the user's mastery session or resumes the open one. A session stays open until a check-in uses it, so closing the app or reopening cook mode can't reset the reveal count.
- `POST /api/mastery/sessions/:id/reveal` records the reveal in `mastery_sessions` before it returns the step's real content.
- The check-in sends `mastery_session_id`. A trigger copies `hidden_steps` and `revealed_steps` from the session, rejects counts sent without a session, and lets each session back only one check-in. The older client-sent `mastery: { hidden_steps, revealed_steps }` is still accepted so old builds don't fail, but it is ignored and earns no badge.
- Deleting an account or a saved recipe that has a mastery check-in succeeds (migration `20261116150000_check_in_mastery_session_delete.sql`). The immutability trigger still blocks a direct change to the session link or the copied counts, but it allows the foreign key to clear `mastery_session_id` when the session row itself is deleted.
- `get_badges_for_user` is unchanged: the badge needs a final-slot check-in with counts and `revealed_steps = 0` (migration `20261115210000_mastery_badge_zero_reveals.sql`). New counts can only come from a session, so that rule is now checked by the server. Check-ins saved before this migration keep their old client-reported counts.
- Clients can no longer insert `check_ins` directly or read `user_recipes.recipe_json`. Only the AI server writes check-ins, and it was already the only caller.
- Badge rules are Ian's area; Ian still needs to OK the zero-reveals rule (Trent decided it on Nov 15, 2026).

*Client (`app/`, UI Direction A):* slot 10 (`is_final`) opens cook mode as a mastery challenge. Before showing a step, cook mode starts or resumes the server session. Steps with `isSafetyStep: true` stay visible. Every other step arrives masked and shows a Reveal control and a "Revealed X of Y hidden steps" indicator. Reveal asks the server for the step; a failed reveal shows an inline error and the step stays hidden. Cook mode and the complete screen say that revealing a step still finishes the challenge, but the mastery seal needs zero reveals. The check-in sends the session's `mastery_session_id`. If cook mode never started a session, none is sent and no badge is earned. Mock mode copies the server: masked steps, sessions, single use. It has a second sign-in (`mastery@simmer.test`) already at slot 10; the default demo user is unchanged.

### F9. Badges
**Acceptance criteria**
- [ ] **Completion badge:** earned for each of slots 1–9 after cooking it and completing the check-in.
- [ ] **Mastery badge:** earned for a final-slot check-in whose server-side mastery session has `revealed_steps = 0` (F8). No session, or any reveals, does not award it.
- [ ] **Path milestone badge:** earned for finishing all 10 slots of "Weeknight basics."
- [ ] A badges screen shows earned badges and locked (grayed-out) ones.
- [ ] Earning a badge shows a short celebration on screen.
- [ ] Each badge can only be earned once.

*Server side:* `badges` is a fixed catalog: 9 completion badges, 1 mastery badge and 1 path milestone. The badge names are placeholders for Ian (open question 12). Earned badges are derived from each slot's first check-in, so a badge can't be earned twice. `get_my_badges()` lists earned and locked badges, and the check-in response lists `badges.earned` for the celebration.

*Client (`app/`, UI Direction A):* session complete shows a seal for each badge in `badges.earned`. The profile lists every badge from `get_my_badges()`, with unearned seals grayed out. Mock check-ins use that same catalog: a completion seal for slots 1–9 only, never a slot-10 completion seal, and the mastery seal only when `revealed_steps` is 0. A code missing from the catalog fails the check-in instead of dropping the seal, and the mock only records mastery as earned after that lookup succeeds.

### F10. Recipe book
**Acceptance criteria**
- [ ] Every recipe the user completes (cooked + check-in done, slots 1–10) is saved to their personal recipe book.
- [ ] Each entry is labeled **Completed** or **Mastered**. Passing the mastery challenge (F8) marks that recipe as Mastered.
- [ ] The recipe book lists saved recipes, and tapping one opens the full recipe (ingredients, steps, videos) in a read-only view.
- [ ] A recipe appears only once, even if the user cooks it again.
- [ ] An empty recipe book shows a message explaining how to add recipes.

*Server side:* `get_my_recipe_book()` returns one entry per completed slot, labeled `completed`, or `mastered` for slot 10. The full recipe is read from `user_recipes`. Clients can't update or delete check-ins, so the history behind badges and the book can't be rewritten.

*Client (`app/`, UI Direction A):* the recipe book lists entries from `get_my_recipe_book()`, newest first: the latest dish as a photo feature, earlier ones as rows, and unfinished path slots under "Still to come". Each row is labeled Completed or Mastered (and shows a cook count on repeats). The screen states that repeats earn 50% XP, up to 100 XP a week. Tapping an entry opens the existing recipe screen. An empty book uses the sentence from the client API doc. A simple bottom bar (Today, Recipe book, You) reaches the book and the profile; Nathan can restyle `app/src/components/tab-bar.tsx`.

## 5. Out of scope (MVP)

Do **not** build these. They're future work.

- Step-ordering exercise ("put the steps in order")
- Cooking levels (L1–L4)
- Weekly leagues and leaderboards, both individual and team
- Per-recipe variations
- Calendar sync (Google Calendar) and grocery cart integration (Walmart or other retailers), and any grocery XP
- The two-week bigger checkpoint
- AI reordering, swapping, or rebuilding the path
- Photo upload of the finished dish, and the "cook it twice" mastery requirement
- Mastery challenges for any recipe other than the final path slot
- More than one learning path
- Hosted LLM APIs (OpenAI, Anthropic, Gemini, etc.)
- Social features (friends, sharing, comments)
- App store publishing (the demo runs through Expo Go or a dev build)

## 6. Tech stack and constraints

| Area | Choice |
|---|---|
| App | React Native with **Expo** (TypeScript, Expo Router), run through Expo Go or a dev build. Lives in `app/`; see `app/README.md` |
| Backend / DB | **Supabase**: Postgres, Auth (email + password), row-level security so users only see their own data |
| AI | **Ollama** running a local model (~7–8B, e.g., a Llama or Qwen model) on **one team laptop** |
| AI server | A small proxy on the same laptop that the app calls. It verifies the user's Supabase login token, calls Ollama with structured JSON output, calls the YouTube API, and writes results to Supabase |
| Network | Phones reach the AI server over the same Wi-Fi or through a tunnel (ngrok or Cloudflare Tunnel). The Expo web build can call the AI server only from origins in `ALLOWED_ORIGINS` (default: Expo dev/web localhost origins on ports 8081 and 19006). Other origins get no CORS headers, and the allowlist never uses `*`. |
| Videos | YouTube Data API v3 (search), with results cached in Supabase |

**App mock mode:** `EXPO_PUBLIC_MOCK_MODE=1` runs the app on typed fake data with no Supabase or AI server (any email signs in; signing in loads a demo user 3 dishes in, creating an account starts fresh). `EXPO_PUBLIC_MOCK_MODE=ai` uses the real Supabase but fakes the AI-server calls. `EXPO_PUBLIC_MOCK_XP_STATUS=failed|skipped` previews the other check-in XP outcomes. The fake slots use the real 10 dishes and XP values; everything else in the fixtures is made up.

**Constraints**
- **Timeline:** ~2 months to a working demo. The team is part-time students.
- **The AI only works while the AI-server laptop is running Ollama and the proxy.** Recipes that are already generated and saved still load without it. `GET /health` only checks that the process is up. `GET /health/deep` reports whether the configured Ollama model answers, whether a cheap service-role read of `path_slots` succeeds, and whether the YouTube key is set. It does not call the YouTube API, and the response has no keys, URLs, or error text. The route stays unauthenticated. It returns HTTP 503 when any check fails and 200 when all are ok. The report (ok or fail) is cached for 5 seconds, and concurrent requests share one in-flight check.
- **Secrets:** The YouTube API key and Supabase service-role key live only on the AI server, never in the app.
- **Preview route:** `POST /api/recipes/generate-preview` is unauthenticated and off unless `ENABLE_PREVIEW_ROUTE=true`. `NODE_ENV=production` keeps it off even when that flag is set, and startup logs a warning.
- **CORS:** The AI server echoes only origins listed in `ALLOWED_ORIGINS`. It never sends `Access-Control-Allow-Origin: *`.
- **YouTube quota:** The default quota is 10,000 units/day, and each search costs 100 units (about 100 searches/day), so searches must be cached.
- **Cost:** Use free tiers (Supabase free plan, YouTube free quota, local model).

**Development workflow (Git)**
- **Nobody commits or pushes directly to `main`.**
- Each feature or change gets its own branch, named after it, for example `feature/f1-signup-onboarding`, `feature/f7-xp-caps`, or `fix/recipe-schema-retry`.
- All commits for that change go on its branch.
- When the change is ready, open a **pull request** into `main`. The PR description lists the feature (F#) and which acceptance criteria are met.
- At least one other teammate reviews and approves the PR before it's merged into `main`.
- Turn on GitHub branch protection for `main` (require a PR and 1 approval) so this is enforced.
