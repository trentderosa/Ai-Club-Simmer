# Simmer — Product Requirements Document (MVP)

*Learn to cook, one dish at a time.*
JMU AI Club · Fall 2026 · Team: Trent DeRosa, Ezzeldin Mallek, Nathan Biru, Ian Bullette, Matthew Munoz
Status: **Draft** · Last updated: 2026-11-21 · Target demo: ~early January 2027 (2 months)

---

## 1. Overview

Simmer is a mobile app that helps new cooks build skills step by step — "the Duolingo of cooking." Instead of a pile of recipes, it gives the user a short, ordered learning path where each recipe teaches a technique, explains why it matters, and links a video showing it.

**Problem it solves:** Many people, especially college students living alone for the first time, want to cook but don't know where to start. Recipes assume basic knowledge ("sauté until fragrant"), recipe apps don't teach skills in a logical order, and nothing keeps beginners motivated, so they fall back on the same few meals or takeout.

**Core loop (MVP):** Plan → Cook → Check in → Level up (XP and badges) → next recipe, with the AI tailoring tips after each check-in. Users can also type a dish outside the path ("Cook anything") and go through the same cook and check-in loop.

## 2. Users

- **Primary:** College students and young adults who are new to cooking, have limited equipment and budget, and cook for themselves.
- **Demo audience:** JMU AI Club members and showcase attendees, who'll see the app run end to end.

## 3. Goals and success criteria

**Goal:** Help a beginner go from needing detailed instructions for every step to cooking a dish with the instructions hidden.

**MVP success criteria (for the showcase):**
1. A brand-new user can go through the full loop on a phone, live: sign up → onboarding → see their plan → cook a recipe with AI-generated steps and a technique video → complete a check-in → earn XP and a badge → see the next recipe's tips reflect their feedback.
2. The user can reach and complete the mastery challenge on the final recipe, earn the mastery badge, and see the recipe in their recipe book.
3. The demo runs without crashes on the demo-day setup (one laptop running the AI server, phones on the same network or tunnel).

(Targets for user testing with people outside the team are an open question.)

## 4. Features

### F1. Sign-up and onboarding
New users create an account and answer a short onboarding form: cooking goals, experience level, kitchen equipment, budget, and weekly schedule (how many days/how much time they can cook). It also asks what they like to eat, from fixed lists: cuisines, kinds of meals, and dietary needs, all optional. After saving, the app calls `personalize_my_path`, which picks each user's dish for every slot they haven't started from a curated catalog. The ten technique slots, their order and XP stay the same for everyone. If that call fails (for example the database doesn't have it yet), the user still reaches Today with the canonical dishes.

**Acceptance criteria**
- [ ] A user can sign up, log in, and log out using Supabase Auth (email + password).
- [ ] A signed-out user can request a password-reset email and, from that link, set a new password in the app.
- [ ] After first sign-up, the user is taken through onboarding before seeing the rest of the app.
- [ ] Onboarding collects: goals, experience level (e.g., never cooked / a little / comfortable), equipment (multi-select checklist), budget (low / medium / high), and schedule (days per week and minutes per session).
- [ ] Answers are saved to the user's profile in Supabase and can be edited later from a settings or profile screen.
- [ ] A returning user who has finished onboarding goes straight to their plan.

*Client (`app/`, UI Direction A):* sign up and sign in are on one screen (email + password). The first name is saved in auth `user_metadata.first_name` for the greeting and the profile, since `profiles` has no name column. Onboarding is steps 2–5 of 5 (about you, what you like to eat, your kitchen, your week) and upserts the user's own `profiles` row with `onboarding_completed: true`, including `cuisines`, `meal_types` and `dietary_needs` (lowercase values from fixed lists; Vegan also selects Vegetarian). It then calls `rpc('personalize_my_path')` and ignores a failure. Editing answers from the profile does the same. Users with `onboarding_completed` not `true` are routed to onboarding; everyone else goes straight to Today. The profile shows those answers and can edit them with the same steps and columns. Sign-out is on the profile.

*Password reset (`app/`, UI Direction A):* From sign-in, Forgot your password asks for an email and calls `supabase.auth.resetPasswordForEmail`. The redirect is the current web origin plus the Expo base path (GitHub Pages `/Ai-Club-Simmer`, or the local origin) and `/reset-password`, the same allow-list as the other auth redirects. The recovery session opens a set-new-password screen (`updateUser`) before Today or onboarding. Full mock mode shows the same confirmation, says it is practice mode, and does not call Supabase or send email. If the auth service has already sent its hourly email limit, the request says to try again in an hour. There is no account deletion.

### F2. Personalized plan (one fixed path)
Every user gets the same path, **"Weeknight basics"**: 10 dish slots in a fixed order (e.g., knife basics, eggs, pasta, stir-fry, …, roast chicken as the final mastery challenge). Personalization comes from how the recipes are written for the user (F3) and from a suggested cooking schedule.

**Acceptance criteria**
- [ ] The 10 path slots (dish name, technique focus, XP value, order) are defined in the database, not generated by the AI.
- [ ] The plan screen shows all 10 slots as **done / current / locked**, matching Figure 2 of the proposal.
- [ ] Only the current slot can be started. Finishing a slot (cook + check-in) unlocks the next one.
- [ ] The plan shows a suggested number of cooking sessions per week based on the user's onboarding schedule.
- [ ] The final slot is marked as the mastery challenge.

*Server side (PR #11, migration `20261115000000_plan_badges_recipe_book.sql`):* a slot is **done** once the user has at least one check-in for it. **Current** is the first slot that isn't done, and everything after it is **locked**. The app reads this with `get_my_plan()`, and `get_my_plan_summary()` gives total XP and the suggested sessions per week (rule in open question 11). The AI server enforces path order: `POST /api/recipes/generate/:slotId` returns `403 SLOT_LOCKED` for a locked slot. Done slots stay open so they can be repeated, and saved recipes always load when the slot is known. If the path-slot lookup comes back empty, the call returns 404 even if a saved recipe exists, so hidden step text is never returned unmasked. See `docs/CLIENT_API.md`.

*Client (`app/`, UI Direction A):* Today reads `get_my_plan()` and `get_my_plan_summary()` and shows the next dish, the suggested sessions per week, total XP, all 10 slots as done / current / locked, and the final slot as the mastery challenge. Locked slots can't be opened. It re-reads both after a check-in. A "Cook anything" card on Today opens the free-form dish flow (F11); it does not change path order. Today, the recipe, cook mode, check-in, the recipe book and the profile sit in one centered column at most 520px wide, so a wide window (the web build) stays aligned; phones use the full width. The bottom bar gives its three tabs equal tap targets.

### F3. AI-generated recipes
When a user opens a path slot for the first time, the app asks the local Ollama model to generate a recipe for that dish, tailored to the user's equipment, budget, and experience. The recipe is saved, and the same saved recipe is used every time after that.

**Acceptance criteria**
- [ ] The AI server calls Ollama with a JSON schema (structured output). The recipe has: title, ingredients (with amounts), time estimate, ordered steps, and for each step: instruction text, an optional "why it matters" note, a `is_safety_step` flag, and an optional technique name for video lookup.
- [ ] The response is validated against the schema. Invalid output is retried up to 2 times, then the app shows a clear error with a retry button.
- [ ] The generated recipe is saved to Supabase for that user and slot, and isn't regenerated on later visits.
- [ ] The prompt includes the user's equipment, budget, and experience, and tells the model not to use equipment the user doesn't have.
- [ ] Steps involving heat, knives, boiling water, raw meat, or hot oil are flagged as safety steps.
- [ ] Generation shows a loading state, and the user can't start cooking until the recipe has loaded.

*Server side:* the AI server now reads the slot and the user's onboarding answers from Supabase (these were stubs that returned nothing, so live generation always failed with 404). The prompt also includes the user's last 3 check-ins, which drive the Coach's note (F6). If Ollama is down, the server log includes the underlying cause (for example `ECONNREFUSED` and the `OLLAMA_BASE_URL` host); the client still gets a generic generation error. Every model call (path recipes, Cook anything, coach notes) shares one queue (`OLLAMA_MAX_CONCURRENT`, default 1; `OLLAMA_MAX_QUEUE`, default 3 waiting). The per-call Ollama timeout starts when a call gets a slot, so time in the queue never counts toward that timeout, and a busy answer is never retried. A normal failed attempt (bad JSON, schema failure, Ollama error) is still retried, and each retry waits in the queue again, up to `OLLAMA_QUEUE_TIMEOUT_MS` (default 60 s) per attempt. A per-request budget, `OLLAMA_REQUEST_BUDGET_MS` (default 170 s, below the app's 193 s recipe timeout that also covers about 8 s of video lookup), caps queue time plus Ollama time for the whole request: each attempt's wait is the smaller of the queue timeout and the budget left minus one Ollama timeout, and no attempt starts once that is zero or less. If an earlier attempt already failed, that failure is returned (logged as `recipe_generation_budget_exhausted`); otherwise the answer is busy. When the queue is full or a wait passes its limit, the recipe route answers HTTP 503 `GENERATION_BUSY` with `Retry-After` and does not retry.

*Server side, prewarm:* after a path check-in is saved (and not on an idempotent replay), and after its Coach's note is made, the server writes the user's next slot recipe in the background so the first open is already saved. The next slot is the one that follows in path order (`slot_order`, not the id), and slot 10 is included. It is skipped, with a `recipe_prewarm_skipped` log reason, when there is no next slot, the next slot is not unlocked, a recipe is already saved, the profile is missing, or the model is not idle. It never waits in the queue (a busy answer just stops it, logged as `recipe_prewarm_failed` with type `busy`), stops retrying as soon as anyone else is waiting for the model (`recipe_generation_retry_skipped`), and is cancelled as soon as a real request (a recipe, Cook anything or a coach note) has to wait for the model, even when the queue is full or `OLLAMA_MAX_QUEUE` is 0 (that request does not count against the queue, and Cook anything is not refused as busy while only a prewarm is running): the gate aborts the prewarm's Ollama request, which frees the slot, and the prewarm is logged as `recipe_prewarm_failed` with type `preempted`, not retried and not saved. The cost is that the cancelled work is discarded. A recipe request that had joined the prewarm then starts its own generation within its remaining time budget instead of failing. The same rerun happens, for each joining request, when the joined prewarm ends `busy` or stops retrying early (`recipe_generation_retry_skipped`); several joiners share one rerun and `recipe_joined_generation_rerun` is logged once per joining request that reruns or joins a rerun, not once per rerun (slot id and reason only). A prewarm that stops retrying early never saves a flagged-rinse fallback: it fails with `retrySkipped` so a joiner reruns clean (a prewarm alone saves nothing and the user's own open generates). A joiner that finds a newer prewarm already registered waits for it and, if that prewarm was preempted, busy or stopped retrying early, reruns once itself (joiners share that rerun) instead of returning the prewarm's failure; any other failure of the newer prewarm is returned as is. A prewarm that failed for model reasons (bad output or Ollama errors, including when its own budget ran out after such failures) is not rerun, and a joiner of a non-prewarm generation just gets the shared result. It uses the same single-flight generator, time budget and video lookup as the recipe route, so opening the recipe during a prewarm joins it instead of starting a second model call (the joiner is not in the queue, so retries continue unless another request is waiting). The check-in is already saved, so its text feeds the recipe prompt as usual. It never delays or fails the check-in response; errors are logged only (`recipe_prewarm_failed`, error name or type only, never the message). `RECIPE_PREWARM` (default on; `false`, `0` or `off` disables it) is also off with stub auth or without Supabase.

*Generation quality and safety (server side):* the prompt forbids telling the user to rinse or wash raw chicken, poultry, or meat (pat dry with paper towels instead), describes recent check-in ratings in words (easy, okay / mostly fine, hard), and tells the model the coachNote may only mention feedback that is in the data it was given (no invented ratings or feelings). After validation and before the safety and slot 10 hideable-step checks, the server cleans model quirks: it trims ingredient names and amounts, strips a leading "Simmer:" or "Simmer -" from the title, and strips a "techniqueName:" label and splits a camelCase technique name ("panToasting" becomes "pan toasting"); an empty technique name is dropped. Cleanup never changes step instructions, step count, or safety flags, and a cleaned recipe that no longer passes the recipe schema is discarded in favor of the original. Each rejected attempt (invalid JSON, schema failure with issue paths and codes only, or an Ollama error) is logged with its attempt number, and a success after retries is logged once, so slow generations can be explained. The safety flagger marks a generated step that rinses or washes chicken, poultry, meat, or bird, including "rinse the chicken", and retries that attempt within the same 3 tries; if every attempt still rinses, the flagged step is the saved fallback and slot 10 cannot hide it. A poultry doneness step that gives no temperature is marked so slot 10 cannot hide it, and a safe sentence such as "pat dry" or "do not rinse" does not clear the dangerous step or hide the only safe instruction. The photo and dish-video lookup starts at the same time as generation instead of after it.

*Client (`app/`, UI Direction A):* the recipe screen calls `POST /api/recipes/generate/:slotId` with the user's access token, shows a loading state while the recipe is written (with a longer message after a few seconds), and maps each error to a screen: Retry for `500`, sign in again for `401`, back to the path for `403 SLOT_LOCKED`, and finish onboarding for the onboarding `404`. The Coach's note (F6) shows above the ingredients.

*Server side (validation errors):* a bad slot id or request body on the recipe routes returns `400` with the existing `error` text and `details` as one short fixed message (`One or more fields are missing or invalid.`), not the raw validation issues. The issue paths and codes (no input values) are logged on the server. The app doesn't read `details`.

### F4. Technique videos
Each recipe step with a technique name gets an instructional video found through the YouTube Data API.

**Acceptance criteria**
- [ ] For each distinct technique in a recipe, the AI server runs one YouTube search (e.g., "how to dice an onion beginner") and saves the first result whose title matches that technique. A poor match is not saved. The step still works with no video.
- [ ] To protect the daily YouTube quota, one recipe opening makes at most 6 new technique searches (`MAX_VIDEO_SEARCHES_PER_RECIPE`). Techniques past the cap are not saved as "no video" (`video_search_skipped_cap` is logged), so they are searched on a later visit once the first ones are cached.
- [ ] Each path recipe and each Cook anything recipe also gets a "Watch someone make it" section with 1–3 YouTube videos of that dish (search: "{dish} recipe"). Videos must be embeddable, safe-search strict, and about 3–20 minutes, preferring higher view counts. The title has to name that dish, not a different one. The section is hidden when the search fails, the quota runs out, or nothing matches. The YouTube key stays on the AI server.
- [ ] Video results are cached per technique so the same search isn't repeated for other users (this saves API quota).
- [ ] In cook mode, a step with a video shows a thumbnail or button that plays the video inside the app.
- [ ] If the search fails or returns nothing, the step still shows without a video and the recipe keeps working.
- [ ] A failed search (quota, network, timeout) is not saved as "no video". The recipe's videos are saved only when every technique got an answer, so a failed lookup is retried the next time the recipe is opened.
- [ ] Video lookup never holds up a recipe for long: a recipe's searches run at the same time under one time budget (default 8 seconds), and the recipe is returned with whatever videos were found by then.

*Server side:* the technique search query is "how to {technique} beginner cooking" (safe search, embeddable videos only). The call asks for up to 5 results, then one `videos.list` for duration when a title is worth checking, and keeps the first hit whose title includes every meaningful word of the technique as its own word ("dice" matches "diced", "knead" matches "kneading", "onion" matches "onions"; "pho" does not match "phone"). A clip under 60 seconds, or a title marked Shorts, is kept only when the title is a technique demo (how to, tutorial, guide, step by step, beginner, technique, or demo). A hit that names a different dish is dropped ("fried rice" is not a video for the technique "cook rice"). If every hit is rejected, that technique is a genuine "no result" and the recipe still returns with no video on that step. Results, including "no result", are cached per technique in `technique_videos`; a cached "no result" is retried after 7 days. A recipe makes at most 6 new technique searches, run concurrently under `VIDEO_LOOKUP_BUDGET_MS` (default 8000 ms). Videos are saved in `user_recipes.video_ids` (and Cook anything's `user_generated_recipes.video_ids`) and returned as `videos[techniqueName]`, but only when the lookup is complete: if any search failed, timed out, ran past the budget or was skipped by the cap, `video_ids` stays empty and the lookup runs again on the next visit (searches that worked are already in the shared cache). A map already saved on the recipe is checked on the next read: a titled video that does not name its technique is left out and the lookup runs again, still at most 6 new searches. A stored video with no title is kept. The column is replaced only when that lookup finishes; it is not cleared. A genuine "no result" counts as complete. Requires `YOUTUBE_API_KEY` on the AI server; without it, recipes have no videos.

Dish videos use one more search per normalized dish name, "{dish} recipe", plus one `videos.list` call for duration and view count. Up to 3 embeddable videos between 3 and 20 minutes are returned as `dish_videos`, highest view count first, and only when every meaningful dish word appears in the title as its own word (endings of cooking verbs count, so "Roasted Chicken" names roast chicken, while a noun stays as written, so "Rolled Egg Omelette" is not egg roll; the tightest window of those words is used, so "Rice cooker hack: Chicken Fried Rice" names fried rice) and the title is not a different dish. Cached technique and dish videos are checked the same way on read, with no YouTube call: an off-target cached technique video is a miss and is searched again, and a dish whose cached videos all fail is searched again. A protein or another dish name between those words drops the hit ("fried chicken and rice" is not fried rice; "chicken noodle soup" is not chicken soup), as does another dish named in the title ("scrambled eggs fried rice" is not scrambled eggs). A closer variant still matches ("egg fried rice", "tomato basil soup", "chicken pho"). The 3–20 minute window still drops very short clips. They are cached in `dish_videos` (migration `20261117201646_dish_videos.sql`, service-role only, RLS on, no client policies). An empty result is cached and retried after 7 days. Quota errors, timeouts and other failures are not cached; a failed search uses a short per-dish cooldown, and a `quotaExceeded`/`dailyLimitExceeded` error pauses every dish search and every technique search until the YouTube quota resets (midnight Pacific). That pause, and each search that is about to run, is stored in `youtube_search_quota` (migration `20261121180000_youtube_search_quota.sql`, service-role only, RLS on, no client policies) so a restarted AI server keeps the same pause. The AI server calls `claim_youtube_search` and `record_youtube_quota_cooldown` with the service role. If that table cannot be read or the pause cannot be saved, the server skips the YouTube call, returns an empty video list for the lookup, and still returns the recipe. YouTube request timeouts stay as they are. Apply the migration after merge. The app hides the section. The key is never sent to the app and is not an `EXPO_PUBLIC_` variable.

*Client (`app/`, UI Direction A):* a step's video is `videos[step.techniqueName]`; a missing entry just means no video, and `null` is treated as `{}`. The recipe screen also shows "Watch someone make it" when `dish_videos` has 1–3 entries, and hides that section when the array is missing or empty. Thumbnails come from `i.ytimg.com`. Tapping opens YouTube with React Native `Linking` only when the URL is on the allowlist (`https://www.youtube.com`, `https://youtube.com`, `https://m.youtube.com`, `https://youtu.be`); the server validates the same list. Mock placeholder videos are disabled and do nothing (no crash, no error toast).

### F5. Cook mode
A step-by-step screen the user follows while cooking.

**Acceptance criteria**
- [ ] Shows the ingredient list first, then one step at a time with Next/Back buttons.
- [ ] Each step shows its instruction, its "why it matters" note (if any), and its video (if any).
- [ ] Safety steps are visually marked (e.g., red border and a "Safety" label).
- [ ] The final step leads to a "Done cooking" action, which opens the check-in (F6).

*Client (`app/`, UI Direction A):* cook mode shows one step at a time with Next/Back, the step's "why it matters" note, a red-bordered Safety box on safety steps, the step's video, highlighted ingredient words, and an inline countdown timer when the step text names a time (e.g. "about 3 minutes"). The last step's button is Done cooking, which opens the check-in.

### F6. Feedback check-in and tip adjustment
After cooking, the user does a quick check-in. The AI uses it to rewrite tips for the next recipe. The path order never changes.

**Acceptance criteria**
- [ ] The check-in asks for a difficulty rating (easy / OK / hard), "What went well?" (optional text), and "What was hard?" (optional text).
- [ ] The check-in is saved to Supabase with the user, recipe, and timestamp.
- [ ] Completing the check-in marks the slot as done, unlocks the next one, and awards XP (F7).
- [ ] When the next recipe is generated (F3), the prompt includes the user's recent check-ins, and the recipe includes a short "Coach's note" at the top that references them (e.g., "Last time heat control was tricky, so watch for…").
- [ ] If the user rated the session "hard," the app suggests repeating that recipe before moving on. The user can accept or skip.
- [ ] Check-ins don't reorder, swap, or remove path slots.
- [ ] The Coach's note falls back to the standard note when the model is busy or its time budget (`OLLAMA_COACH_NOTE_BUDGET_MS`, default 120 s, inside the app's 200 s check-in timeout) runs out; the check-in never fails (see F3 server notes and Constraints).

*Server side:* the check-in response includes `suggest_repeat: true` when the rating is "hard". The app offers "cook again" (the slot stays open) or "skip". Nothing on the path changes either way.

*Coach's note on check-in (server side):* the note prompt includes the dish name (the slot's dish, or the Cook anything dish) and the user's onboarding equipment list, and tells the model to suggest only tools from that list and never a mandoline or other specialty slicer for beginners. If the dish or equipment lookup fails, the note is still written without it and the check-in is never failed. A note that tells the cook to rinse or wash raw chicken, poultry, meat, pork, beef, lamb, steak, chops, drumsticks, wings, breasts, bacon, or sausage is rejected and retried within the same attempt limit and timeouts; if every attempt still says so, it is rewritten to pat the protein dry with paper towels. Washing hands, a board, a surface, a knife, a utensil, or a thermometer stays, and so does rinsing rice, fish, or shrimp, or a warning not to rinse, including "don't rinse or wash" and "rather than rinsing". Rinsing "it" still counts when that sentence names the protein. A negation of something else, and "don't forget" or "never skip", does not hide that rinse.

*Client (`app/`, UI Direction A):* the check-in screen sends the rating and optional notes (max 500 characters) to `POST /api/check-ins`, after reading `user_recipes.id` for the slot. Each attempt gets a client-generated `idempotency_key` (from `expo-crypto`, so it works on Hermes as well as web) that is reused on Retry, so a timed-out check-in cannot be saved or awarded twice. After a network or timeout error the screen re-reads `get_my_plan()` and goes to session complete without posting again if that slot's `times_completed` already went up. If saving takes more than about 15 seconds, the screen explains that the coach is writing a note. When `suggest_repeat` is true, the session-complete screen asks "That one was tough. Cook it again before moving on?" with Cook again and Skip.

### F7. XP with caps
Users earn XP for finishing recipes. Harder recipes are worth more, and repeating easy recipes is capped so users can't farm XP.

**Acceptance criteria**
- [ ] Each path slot's XP is computed from its inputs in `path_slots` (steps, ingredients, and cook_minutes) with the approved formula:

  XP = max(1, round((steps×0.45 + ingredients×0.35 + cook_minutes×0.2)×10))

  The weights (0.45, 0.35, 0.2) and the ×10 multiplier live in `xp_config`. PostgreSQL `NUMERIC` `round()` rounds halves away from zero. The formula applies only when steps, ingredients, and cook_minutes are all set; slots missing an input keep their stored `xp_value`. Current slot inputs and XP, in path order (steps / ingredients / cook_minutes):

  1. Knife Basics Salad — 6/10/20 → 102
  2. Scrambled Eggs — 7/3/10 → 62
  3. Pasta with Sauce — 4/6/18 → 75
  4. Stir-Fry Vegetables — 6/13/35 → 143
  5. Grilled Cheese — 4/3/18 → 65
  6. Rice Bowl — 6/8/25 → 105
  7. Sheet Pan Vegetables — 5/11/38 → 137
  8. Seared Chicken Breast — 5/5/20 → 80
  9. Simple Soup — 5/13/40 → 148
  10. Roast Chicken — 3/2/80 → 181
- [ ] XP is awarded once per completed check-in for that slot.
- [ ] Repeating an already-completed recipe earns 50% of its value, up to a weekly repeat cap of 100 XP per week. Confirmed in Ian's final XP spec (gamification owner), relayed Nov 10, 2026; implemented in PR #5 (merged ca3deff, migration 20261110210000_xp_formula_weights.sql). Repeats over the cap earn 0 XP, and the app says so.
- [ ] The user's total XP is shown on the plan screen, and XP gains show briefly after a check-in.
- [ ] XP is calculated and saved on the server side, not trusted from the client. `award_slot_xp` is EXECUTE-granted to `service_role` only (PR #6, merged as `7fb5b24`). The client never calls it, and only the ai-server awards XP.
- [ ] After a check-in is saved, the AI server awards XP by calling `award_slot_xp` with the service role (the client never calls it). If the award fails, the check-in stays saved and the error is logged.
- [ ] The AI server's `award_slot_xp` call times out after `XP_AWARD_TIMEOUT_MS` (default 5000 ms). A timeout counts as a failed award: the check-in stays saved, the response says `xp: { status: "failed" }`, and `xp_award_failed` is logged with `reason: "timeout"`.
- [ ] Failed or missing awards are retried by the reconcile job (`npm run reconcile:xp` in `ai-server/`). It finds path check-ins with no `xp_events` row and Cook anything check-ins with no `generated_recipe_xp_events` row, created in the lookback window (default the last 168 hours, skipping ones younger than 120 seconds, at most 100 per run across both), never-attempted first, then least recently attempted, then oldest, so check-ins that keep failing can't starve newer ones. Each failed award is counted in `xp_award_attempts` (attempts, last attempt time, a short reason code); a failed check-in is retried only after a backoff gap of `XP_RECONCILE_RETRY_BASE_MINUTES` (default 10, range 1-1440) times 2^(failures-1), capped at 24 hours, so a short outage can't burn its attempts in minutes; a check-in that has failed `XP_RECONCILE_MAX_ATTEMPTS` times (default 15, range 1-100, which spans about 7.8 days of retries, past the 168-hour lookback) is given up on, and the run logs the count and up to 20 of those check-in ids. The chosen batch is processed oldest first. When a run's batch was full and made progress (something awarded or already awarded), the server schedules one follow-up run about 5 seconds later (at most 3 in a row) instead of waiting the whole interval. It re-runs `award_slot_xp` or `award_generated_recipe_xp` with the service role. Running it again, or twice at once, never double-awards: `UNIQUE(check_in_id)` on each XP table rejects a second award, and the job counts that as already awarded. The AI server also runs the job on a timer (`XP_RECONCILE_INTERVAL_MS`, default every 10 minutes, `0` = off; first run one interval after start, runs never overlap, errors never stop later runs), and the CLI stays available. Server side (migration `20261118120000_xp_award_attempts.sql`, apply after merge): server-only `xp_award_attempts` table (RLS on, no client policies, no anon/authenticated access) and four service-role-only functions for the scan, the given-up count, the given-up ids and recording an attempt. XP rules, caps and `UNIQUE(check_in_id)` are unchanged. Because the scan now prefers never-attempted check-ins, a newer check-in can be awarded before an older one that keeps failing; first-vs-repeat still follows check-in order inside each batch.
- [ ] Client roles (`PUBLIC`, `anon`, `authenticated`) have `EXECUTE` revoked on `public.rls_auto_enable()`, the event-trigger helper owned by Nathan and Ezzeldin. The function body is unchanged, and the revoke is guarded so it is a no-op on databases that don't have the function. Approved by Trent on Nov 12, 2026.

*Client (`app/`, UI Direction A):* Today shows total XP. Session complete shows `+xp_awarded` when `xp.status` is `awarded`, explains half-XP repeats and the weekly cap, and shows the totals before and after. ### F11. Cook anything (free-form dish)
The user can type a dish name from Today and get an AI-generated recipe fitted to their kitchen, then cook it and check in through the same screens as a path slot. The 10-slot path is unchanged.

**Acceptance criteria**
- [ ] A busy model returns HTTP 503 `GENERATION_BUSY` with `Retry-After` (see F3 server notes and Constraints for the queue, the per-request budget, and when the 5 per hour limit is charged or refunded).
- [ ] Today has a "Cook anything" entry. The user types a dish (empty, junk, and injection-like input are rejected; the trimmed name is capped at 80 characters). The screen has loading, empty, and error states.
- [ ] The AI server generates the recipe through the existing Ollama recipe path and looks up YouTube videos the same way as a path slot. The first validated recipe for that user and normalized dish name is reused (`cached: true`); a later request or "reroll" cannot change the stored steps, ingredients, minutes, or XP.
- [ ] Dish names are normalized as lowercase, trimmed, collapsed whitespace, punctuation stripped. The recipe is owner-only (RLS). Uncached generations are rate-limited per user (default 5 per hour). That count is stored in the database and still applies after an AI server restart.
- [ ] After cooking, the user checks in through `POST /api/check-ins` with `generated_recipe_id` (not a path `slot_id`). Check-ins are idempotent, the same way as path check-ins.
- [ ] Free-form XP uses the same slot formula, `max(1, round((steps×0.45 + ingredients×0.35 + cook minutes×0.2) × scale))`, from `xp_config`. Steps and ingredients are counted from the validated saved recipe arrays, not a model-reported number. Counts used for XP are clamped to explicit config bounds (steps 1–10, ingredients 1–12, minutes 1–45); the saved recipe body is not truncated. Example: the mock recipe (5 steps, 6 ingredients, 20 minutes) has xp_value 84. An inflated 50/80/999 response stores the full recipe and an xp_value of 177, below roast chicken (181). The daily cap (`freeform_daily_cap`, default 200) still applies when today's slot XP plus free-form XP would exceed it, so a lone max award of 177 is not itself capped.
- [ ] Repeats of the same normalized dish earn 50% XP and share the existing 100 XP/week repeat cap with path-slot repeats. Free-form awards also apply a daily cap (`freeform_daily_cap`, default 200) that counts today's slot XP and free-form XP together. Awards run only on the server via the service role (`award_generated_recipe_xp`). The 10-slot path first-completion awards are not blocked by the daily cap.
- [ ] If `award_generated_recipe_xp` fails after the check-in is saved, the check-in stays saved (`xp.status` `failed`) and the same reconcile job retries it. A second award is rejected by `UNIQUE(check_in_id)` on `generated_recipe_xp_events`. When that duplicate row is read back, `capped` is reported the same way the live award did (the stored XP is compared with the recipe's uncapped first or repeat amount); if the recipe can't be read, only a 0-XP repeat is treated as capped); XP rules and caps are unchanged.
- [ ] Video cards open allowlisted YouTube URLs only. Mock placeholders do nothing gracefully.
- [ ] Every recipe screen that shows a dish background (path recipe, Cook anything recipe, Today’s next dish, and the recipe book) uses a Wikimedia Commons photo of that dish when one matches. Licenses stay CC0, public domain, CC BY, or CC BY-SA, and the image URL stays on `https://upload.wikimedia.org/` (a `thumb.wikimedia.org` thumb is rewritten onto that host, or the original upload URL is used). The credit line is `Photo: <author> · <license>` and, on the recipe hero, is tappable to the Commons file page. Recipe-book row thumbnails leave that line off the small image, because it does not fit there, and show `Photo: <author> · <license>` as a caption under the row byline. If a row's image fails to load, the thumbnail and that caption both switch to the cutting-board photo and its credit. The detail screen, the book's featured photo, and the recipe heroes still show it too. Lookup tries the dish name and then a more specific query (for example "pho", then "pho soup", then "Vietnamese pho"; "chicken parm" also tries "chicken parmesan"). A genuine miss is cached for 7 days so later visits don't search again; timeouts and other errors are not cached. If no image is found, the lookup fails or times out, or the image fails to load, the background falls back to the cutting-board photo (`board.jpg`). A failed lookup never fails recipe generation. Cook mode has no dish background.

*Generation (server side):* Cook anything recipes use the same no-rinse food-safety rule in the prompt and the same post-validation cleanup as path recipes (F3).

*Server side (migration `20261115180000_cook_anything.sql`):* `user_generated_recipes` is unique on `(user_id, normalized_dish_name)`. A BEFORE INSERT trigger clamps counts and freezes `xp_value`; a BEFORE UPDATE trigger refuses to raise those inputs. `get_user_total_xp` and `get_my_plan_summary` include free-form XP. Clamp bounds were set by Trent (1–10 / 1–12 / 1–45 → xp_value 177, below the hardest path slot, roast chicken at 181). The daily cap remains 200. When two saves of the same dish race, the losing insert returns the already-saved recipe instead of failing.

*Server side (migration `20261120150000_cook_anything_generation_limits.sql`, apply after merge):* each allowed uncached Cook anything generation is one row in `cook_anything_generation_hits` (service-role only, RLS on, no client policies). The per-user window (default 5 per hour) is the same after a restart and across processes. A saved dish does not count. If the count cannot be saved, the server refuses the new generation (`503`) instead of falling open. A request that ends busy before any model output (the queue filled right after the check, or the first attempt's queue wait timed out or found the queue full) is refunded: the server calls `refund_cook_anything_generation` (migration `20261121200000_cook_anything_generation_refund.sql`, apply after merge), which deletes the user's most recent hit in the window, and still answers `503 GENERATION_BUSY`. Only busy before any model output is refunded: a busy answer on a later attempt follows a completed model call (bad JSON, schema failure, or rinse rejection) and stays charged, so a user cannot burn model time beyond the 5 per hour. Validation and Ollama failures still count. The refund is best effort: a failure is logged as `cook_anything_refund_failed` and never changes the response. Until the migration is applied the server logs `cook_anything_refund_unavailable` once and keeps the old behavior (busy requests stay charged). XP amounts, the daily cap (200), and badge rules are unchanged.

*Server side (migration `20261117140000_dish_photos.sql`, apply after merge):* `dish_photos` caches a found Commons photo by normalized dish name, service-role only (RLS on, no client policies). A genuine miss is also stored and retried after 7 days; timeouts and errors are not cached. A found photo is also stored as `photo_json` on `user_generated_recipes` so the app can reload it. Path recipes get the same lookup from the slot’s dish name and return it as `photo`. Today and the recipe book call `POST /api/dish-photos`, which only looks up the caller’s path-slot and Cook anything dish names and is rate-limited per IP before auth (default 60 per minute) and per user after auth. Lookup timeout is `DISH_PHOTO_LOOKUP_TIMEOUT_MS` (default 2500 ms). A server-wide cap, `DISH_PHOTO_COMMONS_MAX_PER_MINUTE` (default 60, range 1 to 10000, no off value), limits actual outbound Commons requests across all users; at the cap a lookup returns no photo, is not cached, and retries after the short per-dish cooldown. No API key.

*Recipe book (F10):* once a Cook anything dish has a check-in it is listed in the recipe book next to the path recipes, once per dish, and opens a read-only view with the user's check-in history and Cook again.

*Client (`app/`, UI Direction A):* Today opens `/cook-anything`. A successful generate goes to `/generated/[recipeId]`, then `/generated-cook`, `/generated-check-in`, and `/generated-complete`. Path and Cook anything recipe screens, Today’s next-dish card, and the recipe book use `photo` when it is a Commons raster, and `board.jpg` otherwise. Mock mode returns a canned 5/6/20 recipe worth 84 XP, a canned Commons-shaped photo, a canned dish video, and reuses both on the same normalized name (the dish "invisible stew" returns no photo so the fallback can be checked).

### F8. Mastery challenge (final path recipe only)
The user cooks the final recipe with the steps hidden, revealing individual steps only when they need help. Safety steps always stay visible.

**Acceptance criteria**
- [ ] Only the final path slot (slot 10) is a mastery challenge.
- [ ] In challenge mode, all steps start hidden except safety steps, which are always shown (proposal Figure 3).
- [ ] Each hidden step has a Reveal button, and the screen shows "Revealed X of Y hidden steps."
- [ ] Finishing the challenge and completing the check-in completes slot 10. No photo is required. This awards the slot's XP and adds the recipe to the recipe book (F10) labeled Mastered. Path completion and the graduate badge are unchanged, no matter how many steps were revealed.
- [ ] The mastery badge (F9) is awarded only when the final-slot check-in has `revealed_steps = 0`. A check-in without a mastery session earns no badge. XP is not affected.
- [ ] Reveals are tracked by the server. The app never receives a hidden step's text until the user reveals it, and the reveal count on the check-in comes from the server, not the app.

*Server side:* hidden steps are served only on reveal (migration `20261116000000_mastery_sessions.sql`, follow-up to Q4).
- Slot 10 generation requires at least 3 hideable (non-safety) steps after safety flagging (`MASTERY_MIN_HIDDEN_STEPS` in `ai-server/src/mastery/mask.ts`), so the badge can't be earned with nothing hidden. A recipe with fewer is retried within the normal 3 attempts, then fails with the usual generation error. Trivial steps do not count toward the 3: a non-safety step is trivial when its instruction is 4 words or fewer, or starts with serve, plate, enjoy or garnish and is at most 8 words (`isTrivialStep` in `mask.ts`). Trivial steps are still hidden, just not counted. The slot 10 prompt tells the model that heat, knives, raw meat, hot oil, peeling, grating, draining, pan work and roasting steps must be flagged as safety steps and are never hidden. The slot 10 prompt also asks for at least 6 steps. This is a mastery rule pending Ian's OK. Already-saved slot 10 recipes are reused as-is (F3).
- The recipe call for slot 10 returns hidden steps masked: placeholder text, no "why it matters", `isHidden: true`. Technique names stay, so their videos still show. If the path-slot lookup comes back empty, the call returns 404 even when a saved recipe exists, so hidden step text is never returned unmasked.
- Cook mode calls `POST /api/mastery/sessions`, which starts the user's mastery session or resumes the open one. A session stays open until a check-in uses it, so closing the app or reopening cook mode can't reset the reveal count.
- `POST /api/mastery/sessions/:id/reveal` records the reveal in `mastery_sessions` before it returns the step's real content.
- The check-in sends `mastery_session_id`. A trigger copies `hidden_steps` and `revealed_steps` from the session, rejects counts sent without a session, and lets each session back only one check-in. The older client-sent `mastery: { hidden_steps, revealed_steps }` is still accepted so old builds don't fail, but it is ignored and earns no badge.
- Deleting an account or a saved recipe that has a mastery check-in succeeds (migration `20261116150000_check_in_mastery_session_delete.sql`). The immutability trigger still blocks a direct change to the session link or the copied counts, but it allows the foreign key to clear `mastery_session_id` when the session row itself is deleted.
- `get_badges_for_user` is unchanged: the badge needs a final-slot check-in with counts and `revealed_steps = 0` (migration `20261115210000_mastery_badge_zero_reveals.sql`). New counts can only come from a session, so that rule is now checked by the server. Check-ins saved before this migration keep their old client-reported counts.
- Clients can no longer insert `check_ins` directly or read `user_recipes.recipe_json`. Only the AI server writes check-ins, and it was already the only caller.
- Badge rules are Ian's area; Ian still needs to OK the zero-reveals rule (Trent decided it on Nov 15, 2026).

*Client (`app/`, UI Direction A):* slot 10 (`is_final`) opens cook mode as a mastery challenge. Before showing a step, cook mode starts or resumes the server session. Steps with `isSafetyStep: true` stay visible. Every other step arrives masked and shows a Reveal control and a "Revealed X of Y hidden steps" indicator. Reveal asks the server for the step; a failed reveal shows an inline error and the step stays hidden. ## 6. Tech stack and constraints

| Area | Choice |
|---|---|
| App | React Native with **Expo** (TypeScript, Expo Router), run through Expo Go or a dev build. Lives in `app/`; see `app/README.md` |
| Backend / DB | **Supabase**: Postgres, Auth (email + password), row-level security so users only see their own data |
| AI | **Ollama** running a local model (~7–8B, e.g., a Llama or Qwen model) on **one team laptop** |
| AI server | A small proxy on the same laptop that the app calls. It verifies the user's Supabase login token, calls Ollama with structured JSON output, calls the YouTube API, and writes results to Supabase |
| Network | Same-Wi-Fi (`HOST=0.0.0.0`) is for the Expo dev client only. The GitHub Pages app needs the https tunnel, because an https page cannot call an http LAN address. The tunnel on the demo laptop (ngrok or Cloudflare Tunnel, `HOST=127.0.0.1` and `TRUST_PROXY=true`) is pointed at `http://127.0.0.1:3001`. `TRUST_PROXY=true` trusts `X-Forwarded-For` only from a loopback peer, so a direct LAN client cannot spoof its address, including when `HOST=0.0.0.0`. The Expo web build can call the AI server only from origins in `ALLOWED_ORIGINS` (default: Expo dev/web localhost origins on ports 8081 and 19006). The GitHub Pages app is added by listing `https://trentderosa.github.io` (host only, no path). Setting `ALLOWED_ORIGINS` replaces those defaults. Other origins get no CORS headers, and the allowlist never uses `*`. |
| Web build | The Expo web export is deployed to GitHub Pages (`https://trentderosa.github.io/Ai-Club-Simmer/`) by a GitHub Actions workflow on pushes to `main`. It is a mock-mode build until the repo variables for the real Supabase and AI server values are set. The site is public. Before mock mode is turned off, the Pages origin must be in `ALLOWED_ORIGINS` and in Supabase auth redirect URLs. The build fails, and the last good deploy stays up, when a required public value is blank, not https, an `.env.example` placeholder, or a loopback host (`app/scripts/check-pages-config.mjs`). Plain http is rejected for that public build; local dev still allows it |
| Videos | YouTube Data API v3 (search), with results cached in Supabase |

**App mock mode:** `EXPO_PUBLIC_MOCK_MODE=1` runs the app on typed fake data with no Supabase or AI server (`true` and `all` equal `1`, full mock). Any email signs in; signing in loads a demo user 3 dishes in, creating an account starts fresh. `EXPO_PUBLIC_MOCK_MODE=ai` uses the real Supabase but fakes the AI-server calls. `EXPO_PUBLIC_MOCK_XP_STATUS=failed|skipped` previews the other check-in XP outcomes. The fake slots use the real 10 dishes and XP values; everything else in the fixtures is made up.

**Constraints**
- **Timeline:** ~2 months to a working demo. The team is part-time students.
- **The AI only works while the AI-server laptop is running Ollama and the proxy.** Recipes that are already generated and saved still load without it. When a call from Today (the next dish’s photo), the cook flow (recipe, cook mode, Cook anything, or a mastery reveal), or check-in can’t reach that server, times out, or gets HTTP 429 or 503, that screen shows a short message and a way to try again. Today keeps the plan on screen. Check-in keeps the form up, and Save tries again with the same idempotency key. A path check-in timeout still re-reads the plan and skips a second post when that slot’s times_completed already went up. A 503 from the sign-in service includes code `AUTH_UNAVAILABLE` and still says to try again in a moment. An unexpected error while checking sign-in also returns that 503 instead of hanging. The app uses that code for the sign-in message, even when the message text changes. It uses the previous authentication-service wording only when an older server omits the code. A 503 with neither that code nor that wording says the kitchen is unavailable. `GENERATION_RATE_LIMIT_UNAVAILABLE` still says new recipes are paused. `GENERATION_BUSY` (HTTP 503, with an optional `Retry-After` in whole seconds, clamped to 1-300) shows "The kitchen is busy right now. Try again in about N seconds." (or "in a minute" when there is no usable value; the seconds come from `Retry-After`, which the AI server exposes to browsers by sending `Access-Control-Expose-Headers: Retry-After`, so the web build can read it; otherwise the app says "in a minute") with Try again, the same as the kitchen-unavailable 503. Mock mode does not call the server. `GET /health` only checks that the process is up. `GET /health/deep` reports whether the configured Ollama model answers, whether a cheap service-role read of `path_slots` succeeds, and whether the YouTube key is set. It does not call the YouTube API, so it spends no quota and does not change search caching or quota cooldown. The response has no keys, URLs, or error text. The route stays unauthenticated. Ollama and Supabase gate success: HTTP 503 when either fails, HTTP 200 when both are ok. A busy model returns HTTP 503 `GENERATION_BUSY` with `Retry-After` from path generation and Cook anything. A Cook anything request that ends busy before any model output never uses up one of the 5 per hour: one that arrives when the queue is already full skips the limit (that check runs before the limit is charged), and one that finds the queue full right after the limit check, or times out in the queue on the first attempt, has its charge refunded (see F11 server notes). A busy answer after a completed model call (a later attempt) and other failures (validation, Ollama errors) still count. A check-in never waits long on a busy model: after `OLLAMA_COACH_NOTE_QUEUE_TIMEOUT_MS` (default 15 s), or when the queue is full, or when `OLLAMA_COACH_NOTE_BUDGET_MS` (default 120 s, for all attempts together) runs out, the Coach's note falls back to the standard note. The deep health check does not use the queue. A missing YouTube key is `skipped` (`not_configured`) and the overall status is `degraded` (still HTTP 200), so a missing key does not hide an Ollama or Supabase failure and does not fail an otherwise healthy check. The report (ok, degraded, or fail) is cached for 5 seconds, and concurrent requests share one in-flight check.
- **Server error responses:** The AI server returns JSON error responses, with no stack trace or internal message, except when a response has already started streaming. A malformed body is `400` (`INVALID_JSON`), an oversize body (over 100kb) is `413` (`PAYLOAD_TOO_LARGE`), an unsupported charset or `Content-Encoding` is `415` (`UNSUPPORTED_MEDIA_TYPE`), any other client body error is its `4xx` (`BAD_REQUEST`), an unknown route is `404`, and anything unexpected is a generic `500`. `OLLAMA_MAX_TOKENS`, `OLLAMA_TIMEOUT_MS`, `RATE_LIMIT_WINDOW_MS`, and `RATE_LIMIT_MAX_REQUESTS` must be whole numbers in a bounded range or the server refuses to start. Check-ins and mastery also have a per-IP limit before auth (default 60 per window, `PREAUTH_IP_RATE_LIMIT_MAX`, range 1-10000; window `PREAUTH_IP_RATE_LIMIT_WINDOW_MS`, default 60000, range 1000-3600000). An invalid value for the bounded numeric settings, `ALLOWED_ORIGINS`, or the reconcile settings, or a missing production setting, stops startup with one `Config error:` line naming the variable and range (never a value) and exit code 1. On SIGTERM or SIGINT the server shuts down gracefully: it waits up to the model timeout plus 5 s for in-flight requests, and a second signal exits right away. On the first signal the shared model queue closes: every request still waiting for a model slot, and any retry or new request, gets `503` `GENERATION_BUSY` with `Retry-After` (a Cook anything request refused this way before any model output does not use up one of the 5 per hour, as described above), while a call already running keeps its slot and finishes within the model timeout. Running prewarm calls are aborted, and a request that joined one gets the same `503`.
- **Secrets:** The YouTube API key and Supabase service-role key live only on the AI server, never in the app.
- **Local env file:** `npm run dev`, `npm start`, and `npm run reconcile:xp` load `ai-server/.env` when that file exists. Already-set environment variables win, and CI/tests do not require a `.env` file.
- **JWT / JWKS:** This project's Supabase access tokens are ES256. Set `SUPABASE_JWKS_URI` (for example `https://<project-ref>.supabase.co/auth/v1/.well-known/jwks.json`). Without that or `SUPABASE_JWT_SECRET`, the AI server fail-closes at startup to stub in-memory storage, and check-ins stay disabled.
- **Recipe prewarm:** `RECIPE_PREWARM` (default on; `false`, `0` or `off` turns it off). Startup logs `Recipe prewarm: ENABLED` or `disabled` (see F3 server notes).
- **Preview route:** `POST /api/recipes/generate-preview` is unauthenticated and off unless `ENABLE_PREVIEW_ROUTE=true`. `NODE_ENV=production` keeps it off even when that flag is set, and startup logs a warning.
- **CORS:** The AI server echoes only origins listed in `ALLOWED_ORIGINS`. It never sends `Access-Control-Allow-Origin: *`. The Pages origin to add is `https://trentderosa.github.io` (no path). Setting `ALLOWED_ORIGINS` replaces the localhost defaults.
- **YouTube quota:** The default quota is 10,000 units/day, and each search costs 100 units (about 100 searches/day), so searches must be cached. After a quota error, the pause until midnight Pacific is stored in `youtube_search_quota` and survives an AI server restart.

**Development workflow (Git)**
- **Nobody commits or pushes directly to `main`.**
- Each feature or change gets its own branch, named after it, for example `feature/f1-signup-onboarding`, `feature/f7-xp-caps`, or `fix/recipe-schema-retry`.
- All commits for that change go on its branch.
- When the change is ready, open a **pull request** into `main`. The PR description lists the feature (F#) and which acceptance criteria are met.
- At least one other teammate reviews and approves the PR before it's merged into `main`.
- Turn on GitHub branch protection for `main` (require a PR and 1 approval) so this is enforced.
